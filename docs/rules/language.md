# Language rules

The language area of the Validation package: axe-core 4.14.0 `html-has-lang`, `html-lang-valid`,
`html-xml-lang-mismatch` and `valid-lang`, with their ACT rules, and two ACT rules that only a reader can settle. Ids,
tags and impacts come from the axe-core rule table as facts; the text is our own. How to run rules is in
[checker.md](checker.md), the result shape in [results.md](results.md).

| html-has-lang | axe, ACT b5c3f8 | 3.1.1 | serious | static | none |
| html-lang-valid | axe, ACT bf051a | 3.1.1 | serious | static | none |

| element-lang-matches-content | ACT off6ek | 3.1.2 | serious | a person | none |

The last two have our own ids because axe-core has no counterpart.

## Language tags

A *known primary language tag*, which the ACT rules use, is a tag whose first subtag (up to the first hyphen, ASCII white
space around the tag ignored, compared ASCII case-insensitively) is a language in the **IANA Language Subtag Registry**
(RFC 5646). That is the whole test: `en-US-GB` is known (ACT passes it) while `eng` is not (the registry lists a
three-letter code only where no two-letter code exists), neither are `i-lux` (a grandfathered tag, whose first subtag `i`
is not a language), `dutch` and `#1`. The private-use block `qaa`..`qtz` counts as known.

The data is `Rules/Data/language-subtags.json`, generated by `tools/validation/generate-language-subtags.py` from the
registry file with File-Date **2026-09-17** (SHA-256 `755fad43283be7b41ebe3c89ad054b6eaf928f404f9c0edb74799e0eab74beb1`,
8,276 language records, the qaa..qtz range kept as a range). The IANA and IETF Trust licensing statement of 10 November
2021 dedicates the protocol registries to the public domain (CC0 1.0), so the file needs no notice beyond the attribution in
THIRD-PARTY-NOTICES.

The library also tells well-formed from malformed tags (RFC 5646 section 2.1: language, extlang, script, region, variant,
extension, private use, and the 17 irregular grandfathered tags) in the text of a `valid-lang` failure: "unknown primary
language" or "not a well-formed language tag". It does not change the outcome, because the ACT rules judge only the primary
subtag.

## What each rule checks

- **html-has-lang** (ACT b5c3f8). The `html` element of the document has a `lang` that is not empty or only white space.
  Applies only when the document element is `html`. *Fix:* none; the page's language is content.
- **html-lang-valid** (ACT bf051a). When `html` has a non-blank `lang`, it has a known primary language tag. *Fix:* none.
- **html-xml-lang-mismatch** (ACT 5b7ae0). When `html` has a `lang` with a known primary language and a non-empty
  `xml:lang`, the two primary subtags are equal (case-insensitively). `en-GB` against `en-US` passes; the rest of the tag
  is not compared. *Fix:* none. Which of the two is right is content, and removing `xml:lang` would discard it for XML
  consumers.
- **valid-lang** (ACT de46e4). Each element in `body` whose `lang` is not the empty string and which has text of its own has
  a known primary language tag. *Text of its own* means: a text node that is not only white space (Unicode white space,
  so `&nbsp;` alone does not count), or a non-empty `alt` of an `img`, whose nearest ancestor-or-self with a `lang`
  attribute (even an empty one, which means "unknown") is the element, in an element that is rendered. Text that is
  `aria-hidden` or moved off-screen counts; `display: none` or `hidden` text does not. An empty `lang` and a `lang` that
  covers no text are inapplicable. *Fix:* none.
- **html-lang-matches-content** (ACT ucwvc8). When `html` has a known primary language, a person checks that most of the
  page is in it. Always *needs review*; the library has no language detector and does not guess.
- **element-lang-matches-content** (ACT off6ek). Each element in `body` with a known primary language in `lang` and text of
  its own, as in valid-lang, is *needs review* for the same reason.

## Fix decisions

None of the language rules suggests an edit: `lang` values are content. A mismatch between `lang` and `xml:lang` does not say
which is wrong, and an invalid or missing `lang` has no derivable replacement.

## Differences from axe-core and from ACT

- **valid-lang** follows ACT's applicability: an element is checked only when it owns text, and `html` is left to
  `html-lang-valid`. axe-core's one-line description says only that `lang` values are validated, so the axe differential
  may find elements axe checks and this rule does not (an element with `lang` but no text).
- Whitespace around a tag is ignored (`lang=" fr "` is `fr`). A strict reading of RFC 5646 would reject it; browsers hand the
  value to assistive technology unchanged.
- **Not judged from the ACT cases** (listed with reasons in `testdata/act/tables-forms-language-expectations.tsv`): the
  SVG, MathML and XHTML documents that ACT serves with an XML content type (this library parses every input as HTML and
  does not know the content type); an inapplicable case whose page language cannot be told by a program (ucwvc8); and a
  failed case in which the only text sits in a hidden element used as an image name (off6ek).
